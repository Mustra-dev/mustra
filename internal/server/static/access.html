Approvals

An operation a policy parked. It has not run: approving replays exactly what was asked for, under the identity of whoever asked, so the audit trail and every later check name the requester. You cannot approve your own — an approval whose only requirement is being allowed to do the thing yourself is not an approval. A request nobody decides within eight hours expires, because an approval of yesterday's fleet is not an approval of today's.

Remote desktop

—

RDP to Windows, Screen Sharing (VNC) to Macs and SSH to Linux, from a button on each endpoint's page, through the same checks as a shell session: management rights, the shell action group and the Jump Gate policies below (a reason, an approval, a time limit). Every connection is in the audit log. Off until it is set up. Shadowing a Windows session (watching or sharing control of the signed-in user's own session, which Windows asks them to allow) needs no provider: it is always offered under Jump on a Windows endpoint's page, through the same checks, as a command for your own Remote Desktop client.

To turn it on, pick a provider:
  • Guacamole (built in, browser-only — works from a phone or iPad): start it with mustra's stack, docker compose --profile remote up -d guacd guacamole, with MUSTRA_GUACAMOLE_JSON_SECRET set in deploy/.env to the output of openssl rand -hex 16. Then choose Guacamole below and paste the same secret. Mustra serves it at /guacamole/; it needs no hostname of its own and opens only connections Mustra signs.
  • BeyondTrust (Privileged Remote Access or Remote Support): enter your site, e.g. https://access.example.com. The buttons open a Jump session in the BeyondTrust console, which records it and can inject vaulted credentials. Check the generated link against your site's client scripting API documentation.
  • Custom: a URL template for any other gateway or client, with {ip}, {hostname}, {protocol} (rdp, vnc, ssh) and {port}, e.g. rdp://full%20address=s:{ip}.
The endpoints themselves must accept the connection: Remote Desktop enabled on Windows, Screen Sharing on macOS, and an SSH server on Linux.
The endpoint's agent creates a local administrator for the session alone and removes it when the session ends; Guacamole signs in with it, and nobody sees the password. Agent 0.57.40 or newer.
Recordings are listed under Sessions → Remote desktop.

Changing remote desktop access needs the Manage integrations permission.

Access requests

Just-in-time access to one endpoint, for a stated reason, for a fixed number of minutes. Approving starts the clock at the moment of the decision rather than of the request — a window that began while nobody was looking is not just-in-time. An approver may shorten a window but never extend it past its policy. Revoking ends any session using it immediately, rather than waiting for a clock it has just been taken off. You cannot approve your own.

Jump policies

What reaching an endpoint costs: a reason, somebody else agreeing, a time limit. The highest-priority enabled policy covering an endpoint wins; an endpoint no policy covers costs nothing beyond the permission and management rights that already applied. A chat webhook for requests is set under Administration → Settings.

Recorded sessions

Every Direct Connect session, with what was run in it. mustra records the command before it is sent, so one that hangs or kills the agent still leaves a trace. Reading a transcript takes sessions.audit or deploy.manage — an auditor reviews what was run on an endpoint without being able to run anything on it — and opening one is itself recorded in the audit log.

Content sets

A named collection of packages, dashboards and saved queries. Roles reference them: a role holding no content set may use everything, so adding one takes nothing away until you attach it to a role under Administration → Roles. This is what a role may use; management rights are what it may use it on. Sensors work a little differently: they are restricted only once one of a role's sets lists sensors, and then the role may query, filter on and view exactly those. Hostname, OS, IP and the other identity fields stay readable, since every answer needs to say whose it is.

Action groups

An action group is a ceiling on a module, not a permission on a person: it says which endpoints may receive actions from Deploy, Patches, Playbooks, Direct Connect, Enforce or Reveal at all. An administrator is subject to it too, which is the whole point — it is how a domain controller stays out of reach of a module regardless of who is signed in. A module with no action group, or a disabled one, can reach the whole fleet.

Approval policies

Which operations wait for a second person. A policy matches on module, optionally on the computer groups the operation touches, and optionally on how many endpoints it targets — so "any deploy that reaches a domain controller" and "any patch run over fifty machines" are both expressible. Only Deploy, Patches and Playbooks can be gated: those are the operations mustra can park and resume exactly as asked. Deciding takes approvals.decide.
