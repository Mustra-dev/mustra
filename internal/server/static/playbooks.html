Playbooks

A playbook does several things in order, per endpoint, deciding at each step whether the next one still makes sense. Machine seven can be waiting to come back from a reboot while machine three is already finished — a run is not a fleet-wide state machine that halts because one endpoint failed. Nothing new reaches the endpoint: every step is something mustra could already do. What a playbook adds is the patience to wait for a patch to actually finish before deciding whether to reboot.

Triggers

Something other than a clock starting a playbook. An event trigger fires when a Guide item is raised that matches it; a webhook trigger fires when something outside posts to a URL.

Every matching field left empty means any, so a trigger with nothing set fires on everything. That is written here rather than defaulted into quietly. Two guards are not optional and cannot be turned off: a Guide item raised by Playbooks never fires a trigger, because a playbook that raises a notification that starts a playbook is a loop that runs on your fleet until somebody notices; and every trigger has a cooldown of at least 60 seconds, because a vulnerability feed refresh raises hundreds of items in the same second and without one that is hundreds of attempts to launch the same playbook. The cooldown is claimed in a single conditional UPDATE, so two events in the same millisecond cannot both win.

Waiting for approval

A run that has reached an approval step. One decision per run, not per endpoint. The run is parked in the database, not in a goroutine, so a decision that comes tomorrow — or after a restart — still resumes it from exactly where each endpoint stopped, using the steps the run froze when it started rather than whatever the playbook says now.

Deciding needs approvals.decide, never deploy.manage: an approval whose only requirement is being allowed to do the thing yourself is not an approval. The person who started the run cannot approve it.
