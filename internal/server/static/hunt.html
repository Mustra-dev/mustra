Findings

A hunt matches indicators against the sensor snapshots the fleet has already published, so asking “is this hash anywhere in my estate” costs a few queries rather than waking every machine to search its own disk. The limit matters and is worth stating: a hunt sees exactly what the sensors see. A file outside the integrity watch set, or a process that started and exited between two collections, is invisible to it. This finds known-bad where mustra already looks — it is not a filesystem sweep, and it is not real-time detection.

Signal findings

A signal is a behavioural rule evaluated on every process, file, registry, network, DNS and logon event as it arrives — “PowerShell with an encoded command”, “a Run key written”, “a connection to port 4444”. One row per signal per endpoint, counted, so a rule that fires a thousand times overnight is one thing to look at. Acknowledging a row hides it until the signal fires there again.

Live activity

Every process start, reported as it starts rather than at the next snapshot. Identical invocations inside a five-second window collapse into one row with a count — a hypervisor runs systemctl status several hundred times a minute, and “×587” is a fact where five hundred and eighty-seven identical rows are noise. This is the half a timed hunt structurally cannot have: the processes sensor is a snapshot every fifteen minutes, so anything that runs and exits in between never existed as far as it is concerned — and “runs and exits” describes most of what somebody who should not be there does. An indicator on a process name is matched here at exec, so it raises its finding while the thing is still running.

Signals

Rules in the shape object.property condition value, joined with AND, OR, NOT and parentheses, evaluated live against every event of the objects they name. String comparisons ignore case. Operators: contains, not contains, starts with, ends with, equals / == / is, != / is not, matches (regular expression), in [a, b], not in [a, b], and > < >= <= on numbers.
